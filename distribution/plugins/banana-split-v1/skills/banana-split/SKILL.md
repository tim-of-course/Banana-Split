name: banana-split
description: Use Banana Split by default whenever a task calls for subagents, multiple agents, parallel workers, delegated workers, or supervised agent coordination. Use native Codex subagents only when the user explicitly requests native or standard subagents. Provides durable independent Codex contexts, bounded active-turn scheduling, recursive parent-child and peer coordination, shared configuration, parent-reviewed results, and host-mediated Computer Use.

# Banana Split host loop

Keep the main task as the cockpit. Managed agents run in independent Codex threads.

1. Write a standalone root `task` beginning with a short, specific objective, followed by any conversational context it needs. Its first 96 characters become the visible thread name and task label. Optional structured assignment context may go in `details`, which is delivered to the root alongside `task`. The root starts fresh rather than inheriting this conversation. Keep information reserved for later delivery out of both `task` and `details`. Keep host-only responsibilities and their outputs out of managed assignments; delegate only work the managed agent can perform and complete. The root completes its assigned work with banana_finish; do not require it to wait for a terminal workflow, since its finish creates that state. Carry applicable user requirements and restrictions, including preset choices, context source, file ownership, and permitted validation commands, into the root and descendant assignments.
2. Advertise only host capabilities currently callable here. Pass `host_capabilities: {computer_use: true}` when Computer Use is available; otherwise omit it.
3. Start the workflow in the exact workspace. Pass a user-selected `tier` in this initial call so the first root turn uses it; omit only when the configured default is intended. Resolve exact configured tier names first. For the shipped catalog, map "high performance" to `performance-optimized`, "max performance" or "maximum performance" to `max-performance`, "cheap" or "cost optimized" to `cost-optimized`, and "default" to `default`. A request for high performance alone does not select max performance. Use the configured catalog; do not invent tier definitions or silently substitute another tier when the requested one is unavailable. The host may supply `preset_tiers`: three or four tiers sharing four preset names, each mapping to a model, reasoning level, and optional service tier. Four tiers ship by default; three-tier catalogs remain valid for compatibility. Omit `root_preset` to use the configured default; pass a preset name only when the user requests that configured preset. Omit permission overrides to inherit workspace access, or pass restrictions that narrow it. Before restricting writable roots to a new output directory, create that authorized directory; agents cannot create missing ancestors outside their writable roots.
4. Retain the exact returned `workflow_id` and agent IDs; pass them unchanged to later calls. If a call returns `not_found`, compare its ID with the successful start result or `banana_workflow_list` before calling again. Poll until the workflow is mechanically terminal, preserving the returned cursor between calls. Give the user a brief progress summary about once a minute while work runs, and when a milestone or blocker arises: what finished, what is underway, and what needs attention. Summarize the current state rather than narrating each poll. Snapshot capacity and runnable backlog cover the entire runtime across workflows; sampled counts are not historical per-workflow peaks.
5. Prioritize pending approvals and host actions over unrelated transcript reviews or status nudges. Inspect each requested operation before deciding. Use the snapshot's attention items and `next_action`; `pending_context` normally waits for the spawning parent turn to finish, as shown by `context_dependency`.
   - For a Codex approval, inspect the operation against the user's existing authorization; ask for a decision only when authorization is unresolved. For file changes, check `request.file_changes` paths and diff from the native proposal. If absent, use `banana_agent_inspect` with `transcript_limit` and page as needed to match `turn_id` and `request.itemId`; pending patches may be absent from that transcript too, so missing evidence does not authorize approval. Relay the decision with `banana_approval_respond`. Treat an unsuccessful approval tool call as unresolved; report an external approval-review refusal instead of claiming that the native operation was declined. Do not repackage the same decision to bypass that refusal. For command/file approvals, `decline` rejects only the operation and lets the agent continue. Use `cancel` when stopping the agent and its subtree is intended. Approval `details` are inspection records, not agent context; send new context with `banana_workflow_send`, which queues it for the next turn and does not interrupt an active retry. For permission, user-input, and MCP elicitation requests, copy the response shape required by `request.response_contract` into `details.response`.
   - For `host_action_required`, inspect the bounded task and evidence request, then call `banana_host_respond(status: in_progress)` before acting. Perform or decline it under this task's permissions and record `completed`, `declined`, or `failed` with evidence. Resolve an `uncertain` action with final evidence and `completed` or `failed` before claiming other Computer Use work; it retains the queue reservation.
   - A host message to an agent waiting with `no_disposition` creates one continuation. Send only new material context or an explicit resume.
   - Direct parents review submitted children. The host inspects submissions and deep agents when investigating a problem or verifying the final result; inspection does not resume them.
   - A sandbox-denied command that has not been declined by the host may need the managed agent to explicitly request an escalated rerun through its native shell tool before any approval appears. If required work stopped there and its effective policy permits approval, pass that recovery context to an eligible agent or a new follow-up workflow.
6. Apply a user-requested spawn freeze, reopening, subtree cancellation, or workflow cancellation with `banana_workflow_control`. Report cancellation without implying rollback.
   Only the host may change the active tier or its definitions with `banana_workflow_set_tier(workflow_id, tier, preset_tiers?)`. Changes affect new agents and existing agents' next turns; running turns retain their current routing. Agents choose only among the active tier's four presets. Use `banana_agent_inspect` routing history when reporting tier or model changes.
7. Mechanical termination does not by itself complete the user's task. Inspect partial, blocked, or unsuccessful results and address remaining authorized work when possible; a terminal workflow needs a new follow-up workflow. Finish only after the workflow is terminal. Report these separately:
   - mechanical workflow status;
   - root result outcome and summary, if present;
   - workflow ID, root agent ID, and any child IDs needed for later inspection.
   Use the final snapshot and targeted inspections for the recap; retain verified facts instead of rereading unchanged terminal transcripts. Alongside the usual task response, always include a compact workflow recap: the tier or tiers used and any tier changes; whether the catalog was configured or overridden for the workflow; the number of distinct subagents that ran across all depths, with the root coordinator counted separately; the models and reasoning levels used, grouped by distinct agent count with the root separate; and notable events such as revisions, retries, failures, approvals, or host-assisted work. Count resumed agents once in the total; an agent that changes routing may appear in multiple model/effort groups. Use per-turn `routing_history` and tier-change events to account for earlier settings instead of reporting only the final active tier. Distinguish a selected tier on which no turn ran from tiers used. For legacy flat catalogs report "no tier (legacy flat catalog)". Use runtime `diagnostics` for managed tool rejection counts, turns without a disposition (including recovered turns), revisions, and acceptances. Routing history records resolved configuration; report observed model/effort fields when Codex supplies them, and label unconfirmed fields as resolved settings rather than verified model use. When an agent summary conflicts with those counts, report the recorded operations and identify the discrepancy; a message requesting changes is not a formal revision. `preset_catalog_source: configured` means the runtime configuration supplied the catalog; `workflow_override` means the host supplied per-workflow definitions. Identify overrides and catalog changes in the recap. Verify claimed outcomes against the assignment before reporting task success; cancellation does not imply rollback. Mention the host task's model and reasoning level when known, and label unavailable details as unknown.

For MCP startup or permission failures, inspect `banana_workflow_list.runtime` to identify the running executable, data directory, port, and MCP selection. `workspace` selects enabled servers declared in trusted project configuration layers at workflow creation; a fixed array restricts access to those names. Workflow permissions can only narrow the resulting snapshot. Reinstallation does not change an already-running runtime.

If startup returns `runtime_unavailable`, report the configured path and startup error. Leave uncertain turns untouched and keep native subagents unavailable.
